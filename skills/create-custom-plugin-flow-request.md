# Skill: Create a Custom Plugin for Flow Requests

**Name:** create-custom-plugin-flow-request
**Description:** Step-by-step guide to building, testing, and publishing a custom plugin (node) for the Flow Requests workflow platform.

---

## Description

This skill walks you through the complete lifecycle of a Flow Requests custom plugin — from scaffolding the project to having the node available and executable inside the visual workflow builder.

A **custom plugin** is a TypeScript class that the workflow engine treats as a first-class node, indistinguishable from built-ins like HTTP Request, Condition, or Loop. You define what form fields the UI renders (`getConfig`), and what logic runs when the node is executed in a flow (`execute`). The engine resolves your plugin at runtime by matching the node's `type` string to the library name you registered during installation.

The skill covers every stage in detail:

- **Scaffolding** — copying the official `plugin-examples/template`, updating `package.json` with the correct name and entry points, and setting the Webpack UMD library name that the browser runtime uses to locate your class.
- **Class authoring** — implementing `getConfig()` to declare node metadata and all configurable properties (text inputs, textareas, selects, and conditionally visible fields), and implementing `execute()` to carry out the actual work using the resolved settings.
- **Expression resolution** — using `this.parseExpression()` to interpolate `{{ steps.nodeName.output.field }}` template expressions in every string setting, enabling plugins to consume outputs from previous nodes in the flow.
- **Workflow state access** — reading `this.state` to reach environment variables (`envData`), the incoming webhook request (`request`), previous step outputs (`steps`), and Faker.js for test data generation.
- **Runtime-only imports** — using the `/* webpackIgnore: true */` dynamic import pattern for Deno/Node packages (e.g. `npm:postgres`, `node:vm`) that must not be bundled into the browser build.
- **Building** — running `npm run build` to produce both the browser UMD bundle (`dist/bundle.js`) consumed by the Flow Requests sandbox and the Deno bundle (`dist/deno-bundle.js`) used by the remote runner (`run-flow-request-remotely`).
- **Testing** — writing Jest unit tests with `ts-jest` to verify config correctness, input validation, and execution outcomes without a running Flow Requests instance.
- **Publishing and installation** — publishing to npm and serving via jsDelivr/unpkg, or hosting `dist/bundle.js` on any public URL, then registering the plugin in the UI by providing the CDN URL and the library name.
- **Documentation** — writing a human-facing `README.md` (section 13) and a machine-readable `skill.md` (section 12) for each plugin.
- **Common pitfalls** — a reference table of the most frequent mistakes found across the existing plugins (`name`/`type` mismatch, missing `parseExpression` calls, bundling Deno-only modules, etc.) and how to fix them.
- **Pre-publish checklist** — a concise checklist to verify correctness before releasing the plugin.

By the end of this skill you will have a fully working, tested, and installable custom node ready to be dropped into any Flow Requests workflow.

## 1. Conceptual overview

A **plugin** in Flow Requests is a self-contained TypeScript class that the
workflow engine can discover at runtime and execute as a node in any flow.
Every plugin:

- Extends `NodeBase` from `core-package-mini-n8n`.
- Implements two mandatory methods: `getConfig()` and `execute()`.
- Is compiled into two bundles: a browser bundle (`dist/bundle.js`) and a
  Deno-compatible bundle (`dist/deno-bundle.js`).
- Is installed in the UI by pasting a **CDN URL** plus the **library name**
  that Webpack exports.

The workflow engine resolves unknown node types by delegating to
`CustomNodeManager`, which looks up the installed plugins. When the type
matches, it calls `new YourPlugin(state)` and then `execute(nodeInput)`.

## 3. Step-by-step guide

### Step 1 — Copy the template

```bash
cp -r plugin-examples/template my-plugin
cd my-plugin
```

### Step 2 — Update `package.json`

Change `name`, `version`, and `description`. The `main` and `browser` fields
must point to `dist/deno-bundle.js` and `dist/bundle.js` respectively — keep
them as-is unless you rename the output files.

```json
{
  "name": "my-plugin-flow-requests",
  "version": "1.0.0",
  "description": "My custom plugin for Flow Requests",
  "main": "dist/deno-bundle.js",
  "browser": "dist/bundle.js"
}
```

### Step 3 — Set the Webpack library name

Open `webpack.config.cjs` and replace `<CHANGE_VALE_HERE>` with the exact
library name you will enter in the UI when installing the plugin. This name
becomes the global variable that the browser bundle exports.

**This value must be identical to the `name` and `type` fields you set in
`getConfig()`.** All three — `output.library`, `name`, and `type` — must
match exactly, or the plugin will fail to load or execute.

```js
output: {
  filename: "bundle.js",
  path: path.resolve(__dirname, "dist"),
  library: "MyPlugin",        // ← must match name and type in getConfig()
  libraryTarget: "umd",
},
```

### Step 4 — Write the plugin class (`src/index.ts`)

```typescript
import {
  NodeBase,
  NodeConfig,
  NodeInput,
  NodeReturn,
} from "core-package-mini-n8n";

class MyPlugin extends NodeBase {
  constructor(state: any) {
    super(state);
  }

  // ─── getConfig ────────────────────────────────────────────────────────────
  // Declares the node identity and the form fields the UI will render.
  // `name`, `type`, and `output.library` in webpack.config.cjs MUST all be
  // the same string. The workflow engine matches the node `type` to the
  // library name exported by the browser bundle — if any of the three differ,
  // the plugin will not be found or will fail to execute.
  getConfig(): NodeConfig {
    return {
      name: "MyPlugin",   // must match `type` below AND output.library in webpack.config.cjs
      type: "MyPlugin",   // must match `name` above AND output.library in webpack.config.cjs
      description: "Short human-readable description shown in the UI",

      // Optional: used by the AI assistant to understand what this node does
      ai_description: "Detailed description for AI-driven flow generation",

      properties: [
        // --- text field ---
        {
          label: "API Key",
          name: "apiKey",       // key used in node.settings.apiKey
          type: "text",
          required: true,
          default: null,
          ai_description: "Authentication token for the external service",
        },

        // --- textarea field ---
        {
          label: "Payload (JSON)",
          name: "payload",
          type: "textarea",
          required: false,
          default: null,
        },

        // --- select field ---
        {
          label: "Operation",
          name: "operation",
          type: "select",
          required: true,
          default: "send",
          options: [
            { label: "Send",    value: "send" },
            { label: "Receive", value: "receive" },
          ],
        },

        // --- conditionally visible field ---
        {
          label: "Target ID",
          name: "targetId",
          type: "text",
          required: false,
          default: null,
          conditionShow: [
            {
              keyCheck: "operation",       // watched property
              valueExpected: "send",       // only show when operation === "send"
            },
          ],
        },
      ],
    };
  }

  // ─── execute ──────────────────────────────────────────────────────────────
  // Called at runtime by the workflow engine.
  // `node.settings` contains all values the user configured in the UI.
  // Always call `this.parseExpression()` on string settings so that
  // `{{ steps.previousNode.output.field }}` expressions are resolved.
  async execute(node: NodeInput): Promise<NodeReturn> {
    const setting = node.settings;

    // 1. Validate required fields
    if (!setting.apiKey) {
      throw new Error("You must provide an API key");
    }

    // 2. Resolve dynamic expressions in every string value
    const apiKey   = this.parseExpression(setting.apiKey);
    const targetId = setting.targetId
      ? this.parseExpression(setting.targetId)
      : null;

    // 3. Parse JSON fields when needed
    let payload: Record<string, unknown> = {};
    if (setting.payload) {
      try {
        payload = JSON.parse(this.parseExpression(setting.payload));
      } catch {
        throw new Error("payload must be valid JSON");
      }
    }

    // 4. Execute the actual logic
    try {
      const response = await fetch("https://api.example.com/endpoint", {
        method: "POST",
        headers: {
          "Content-Type": "application/json",
          Authorization: `Bearer ${apiKey}`,
        },
        body: JSON.stringify({ targetId, ...payload }),
      });

      const data = await response.json();

      if (!response.ok) {
        return { ok: false, error: data };
      }

      return { ok: true, data };
    } catch (error: any) {
      return { ok: false, error: error.message };
    }
  }
}

export default MyPlugin;
```

## 4. Key API reference

### `NodeBase` (abstract base class)

| Member | Signature | Purpose |
|---|---|---|
| `state` | `protected any` | Shared workflow state (env vars, previous steps, faker, etc.) |
| `parseExpression(expr)` | `(string) → string` | Resolves `{{ ... }}` template expressions using `eval` against `this.state` |
| `getConfig()` | `() → NodeConfig` | Returns the node's metadata and form schema |
| `execute(input)` | `(NodeInput) → Promise<NodeReturn \| LinkedList>` | Main execution logic |

### `NodeConfig`

```typescript
interface NodeConfig {
  name: string;           // must equal type AND output.library in webpack.config.cjs
  type: string;           // must equal name AND output.library in webpack.config.cjs
  description: string;
  ai_description?: string;
  properties: NodeProperty[];
}
```

### `NodeProperty`

```typescript
interface NodeProperty {
  label: string;          // UI label
  name: string;           // key in node.settings
  type: "text" | "textarea" | "select";
  required: boolean;
  default: any;
  options?: Array<{ label: string; value: string }>;  // for type: "select"
  conditionShow?: Array<{                              // conditional visibility
    keyCheck: string;
    valueExpected: string;
  }>;
  ai_description?: string;
}
```

### `NodeInput`

```typescript
interface NodeInput {
  [key: string]: any;
  settings: { [key: string]: any }; // values from the configured UI form
}
```

### `NodeReturn`

```typescript
interface NodeReturn {
  [key: string]: any;
  // Convention used across all built-in and example plugins:
  ok: boolean;
  data?: any;
  error?: any;
}
```

### Accessing workflow state inside `execute`

`this.state` is the live workflow context. Useful paths:

| Expression (in UI) | What it resolves to |
|---|---|
| `{{ steps.myNode.output.data }}` | Output of a previous node named "myNode" |
| `{{ state.envData.MY_VAR }}` | Environment variable set in the flow's env panel |
| `{{ state.request.body }}` | Incoming request body (when flow is triggered via webhook) |
| `{{ state.faker.internet.email() }}` | Faker.js — useful for test data |

## 5. Runtime-only imports (Deno / Node)

If your plugin uses a package that should never be bundled into the browser
build (e.g. `npm:postgres`, `node:vm`, native drivers), use a dynamic import
with the `webpackIgnore` comment so Webpack skips it at bundle time while
Deno/Node resolves it at runtime:

```typescript
const { default: postgres } = await import(
  /* webpackIgnore: true */ "npm:postgres"
);
```

## 7. Write tests

Open `tests/index.spec.ts`. Use Jest with ts-jest (already configured via
`jest.config.cjs`):

```typescript
import { describe, it, expect, jest } from "@jest/globals";
import MyPlugin from "../src/index";

describe("MyPlugin", () => {
  const state = { steps: {}, envData: {}, request: {} };

  it("returns the correct config", () => {
    const plugin = new MyPlugin(state);
    const config = plugin.getConfig();
    expect(config.name).toBe("MyPlugin");
    expect(config.type).toBe("MyPlugin");
    expect(config.properties.length).toBeGreaterThan(0);
  });

  it("throws when apiKey is missing", async () => {
    const plugin = new MyPlugin(state);
    await expect(
      plugin.execute({ settings: {} } as any)
    ).rejects.toThrow("You must provide an API key");
  });

  it("returns ok: true on success", async () => {
    global.fetch = jest.fn().mockResolvedValue({
      ok: true,
      json: async () => ({ id: "123" }),
    } as any);

    const plugin = new MyPlugin(state);
    const result = await plugin.execute({
      settings: { apiKey: "test-key", operation: "send" },
    } as any);

    expect(result.ok).toBe(true);
  });
});
```

Run tests:

```bash
npm test
```

## 8. Publish and install the plugin

### Option A — npm registry (recommended)

```bash
npm publish --access public
```

Once published, your package is immediately available on **unpkg** — a CDN
that serves any file from any npm package using the pattern:

```
https://unpkg.com/<package-name>@<version>/dist/<file>
```

Flow Requests uses **two different bundles** depending on where the flow runs:

| Runtime | Bundle file | unpkg URL pattern |
|---|---|---|
| **Browser** (flow runs in the user's browser) | `dist/bundle.js` | `https://unpkg.com/my-plugin-flow-requests@1.0.0/dist/bundle.js` |
| **Server-side** (flow runs via `run-flow-request-remotely`) | `dist/deno-bundle.js` | `https://unpkg.com/my-plugin-flow-requests@1.0.0/dist/deno-bundle.js` |

You can also omit the version to always resolve the latest published release:

```
https://unpkg.com/my-plugin-flow-requests/dist/bundle.js
https://unpkg.com/my-plugin-flow-requests/dist/deno-bundle.js
```

Using a pinned version is recommended for stability:

```
https://unpkg.com/my-plugin-flow-requests@1.0.0/dist/bundle.js
https://unpkg.com/my-plugin-flow-requests@1.0.0/dist/deno-bundle.js
```

Semantic versioning applies normally — patch for fixes (`1.0.1`), minor for
new fields/operations (`1.1.0`), major for breaking changes (`2.0.0`).

#### Why two bundles?

- `dist/bundle.js` is a **UMD browser bundle** produced by Webpack. It
  contains all npm dependencies inlined and exports your class as a global
  variable (the `library` name from `webpack.config.cjs`). This is what the
  Flow Requests frontend loads dynamically via a `<script>` tag when the user
  installs the plugin.

- `dist/deno-bundle.js` is a **Deno bundle** produced by `deno bundle`. It
  uses native Deno/Node module resolution (`npm:`, `node:` specifiers) and is
  loaded by `run-flow-request-remotely` when the flow executes on the server.
  It does **not** need Webpack-bundled dependencies because Deno resolves them
  at runtime from the npm registry.

### Option B — direct CDN URL

Host `dist/bundle.js` (and optionally `dist/deno-bundle.js`) anywhere
publicly accessible (GitHub Pages, S3, etc.) and use those URLs directly.

### Installing in the Flow Requests UI

1. Open the Flow Requests app.
2. Navigate to **Install Custom Plugins** (or the plugin manager modal).
3. Paste the **unpkg URL** to `dist/bundle.js` (browser bundle):
   ```
   https://unpkg.com/my-plugin-flow-requests@1.0.0/dist/bundle.js
   ```
4. Enter the **Library Name** — this must exactly match the `library` value
   you set in `webpack.config.cjs` (e.g. `MyPlugin`).
5. Click **Install**.

The plugin is now available as a draggable node in the workflow builder.
When the flow runs on the server side, `run-flow-request-remotely` will
resolve the plugin from the Deno bundle URL instead:

```
https://unpkg.com/my-plugin-flow-requests@1.0.0/dist/deno-bundle.js
```

## 9. Common pitfalls

| Pitfall | Fix |
|---|---|
| `name` and `type` in `getConfig()` differ | They must be the same string, and both must also match `output.library` in `webpack.config.cjs`. |
| Webpack `library` name doesn't match `name`/`type` in `getConfig()` | All three must be identical: `name`, `type`, and `output.library`. |
| Webpack `library` name doesn't match UI "Library Name" | The value entered in the UI during installation must also match all three above. |
| `parseExpression` not called on user input | Dynamic `{{ ... }}` values won't be resolved; always call it on every string setting. |
| Browser bundle tries to import a Node/Deno-only module | Use `/* webpackIgnore: true */` in a dynamic `import()`. |
| `deno bundle` fails | Make sure `deno.json` is present and imports are resolvable from the Deno registry. |
| `execute` throws instead of returning `{ ok: false, error }` | The workflow engine catches throws and wraps them, but returning a structured error is more predictable and lets downstream nodes act on it. |

## 10. Full worked example — GitHub plugin (from template)

The `template` plugin comes with a GitHub node that is fully commented-out as
a reference. Uncomment and adapt it when building an API integration:

```typescript
async execute(node: NodeInput): Promise<NodeReturn> {
  const setting = node.settings;
  if (!setting.username) {
    throw new Error("Invalid settings. You need to provide a username");
  }

  setting.username = this.parseExpression(setting.username);
  setting.repoName = this.parseExpression(setting.repoName);

  if (setting.operation === "getRepos") {
    const response = await fetch(
      `https://api.github.com/users/${setting.username}/repos`
    );
    const data = await response.json();
    return { ok: true, data };
  }

  if (setting.operation === "getProfile") {
    const response = await fetch(
      `https://api.github.com/users/${setting.username}`
    );
    const data = await response.json();
    return { ok: true, data };
  }

  if (setting.operation === "getSpecificRepo") {
    try {
      const response = await fetch(
        `https://api.github.com/repos/${setting.username}/${setting.repoName}`
      );
      const data = await response.json();
      return { ok: true, data };
    } catch (error: any) {
      return { ok: false, error: error.message };
    }
  }

  return { ok: true };
}
```

## 11. Checklist before publishing

- [ ] `name` === `type` === `output.library` in `webpack.config.cjs` (all three must be identical).
- [ ] `library` in `webpack.config.cjs` matches the intended UI library name.
- [ ] All string settings pass through `this.parseExpression()`.
- [ ] Required fields validated before use; throw with a descriptive message.
- [ ] JSON fields parsed with try/catch; throw on invalid JSON.
- [ ] Deno-only/Node-only imports use `/* webpackIgnore: true */`.
- [ ] `npm run build` completes without errors.
- [ ] Unit tests written and passing (`npm test`).
- [ ] `dist/bundle.js` hosted at a publicly accessible URL.
- [ ] A `skill.md` is written at the root of the plugin project (see section 12).
- [ ] A `README.md` is written at the root of the plugin project (see section 13).

## 12. Writing a `skill.md` for your plugin

Every plugin should ship a `skill.md` file at the root of its project. This
file is written **for AI agents** — it tells an agent exactly what your plugin
does, what settings it expects, what it returns, and how to wire it into a
Flow Requests automation. Without it, an agent has no reliable way to know
when or how to use your plugin when building flows on behalf of a user.

### Why it matters

When a user asks an agent to "build a flow that sends a Slack notification
whenever a new row appears in Postgres", the agent needs to discover which
installed plugins cover Slack and Postgres, understand what properties to fill
in, and know what output shape to expect so it can chain nodes correctly. The
`skill.md` is the source of truth for all of that.

**Name:** SlackPlugin

## Description

Sends a message to a Slack channel using the Slack Incoming Webhooks API.
No OAuth setup required — only a webhook URL from the Slack app configuration.
Use it whenever a flow needs to alert a team channel about an event, an error,
or the result of a previous step.

---

## When to use this plugin

- Send a notification when an HTTP request node returns an error.
- Alert a channel when a new record is created in a database.
- Post a summary of data collected by earlier nodes in the flow.

---

| Property name | Type | Required | Description |
|---|---|---|---|
| `webhookUrl` | text | yes | Slack Incoming Webhook URL (e.g. https://hooks.slack.com/services/...) |
| `message` | textarea | yes | The message text to post. Supports Slack mrkdwn formatting. Supports `{{ }}` expressions. |
| `username` | text | no | Display name override for the bot. Defaults to the name set in the Slack app. |

Success:
```json
{ "ok": true }
```

Failure:
```json
{ "ok": false, "error": "invalid_payload" }
```

This node only signals success or failure — it does not return data.
Use a Condition node checking `{{ steps.slackNode.output.ok }}` to branch
on whether the message was delivered.

{
  "type": "SlackPlugin",

## 13. Writing a `README.md` for your plugin

Every plugin should also ship a `README.md` at the root of its project. Unlike
`skill.md` (section 12), which is written for AI agents, the `README.md` is
written **for humans** — developers browsing the repository, teammates who
maintain the plugin, and users who find it on npm. It should explain, in plain
language, what the plugin is, what it does, the library name, and how to
configure and use it.

Both files are required. Keep them in sync with each release.

### Required contents

A good plugin `README.md` contains:

1. **Title** — the plugin's display name.
2. **What it is** — a short paragraph explaining what the plugin does and which
   external service or system it integrates with.
3. **Library name** — the exact `output.library` value from
   `webpack.config.cjs` (identical to the `name`/`type` in `getConfig()`).
   State clearly that this is the value to enter in the Flow Requests UI when
   installing the plugin.
4. **Package & CDN** — the npm package name and the CDN URL(s).
5. **Installation** — how to build the plugin and register it in Flow Requests.
6. **Configuration** — a table of every setting (name, type, required,
   description), plus required environment variables and, for `select` fields,
   the available operation options.
7. **Output** — the shape of `{ ok, data }` / `{ ok: false, error }` and which
   fields downstream nodes may reference.
8. **Example** — a minimal flow snippet showing the plugin configured.
9. **Development** — how to install dependencies, run tests, and build.
10. **Caveats** — rate limits, environment variables, server-only operations,
    or other limitations.

Do **not** duplicate the machine-facing detail of `skill.md`; keep the README
concise and human-readable, and cross-reference `skill.md` for agent usage.

### README template

```markdown
# <Plugin display name>

<One paragraph: what the plugin is and which service/system it integrates
with.>

## Library name

Use this exact value as the **Library Name** when installing the plugin in
Flow Requests:

```
<LibraryName>
```

- npm package: `<package-name>`
- CDN (browser): https://unpkg.com/<package-name>@<version>/dist/bundle.js
- CDN (server): https://unpkg.com/<package-name>@<version>/dist/deno-bundle.js

## Installation

1. Build the plugin: `npm install && npm run build`
2. In Flow Requests, open **Install Custom Plugins**.
3. Paste the CDN URL to `dist/bundle.js`.
4. Enter the library name `<LibraryName>`.
5. Click **Install**.

## Configuration

| Setting | Type | Required | Description |
|---|---|---|---|
| `settingName` | text | yes | What to provide and any format requirements |

Required environment variables (reference them with `{{ state.envData.X }}`):
- `MY_VAR` — what it is.

## Output

Success:
```json
{ "ok": true, "data": {} }
```

Failure:
```json
{ "ok": false, "error": "..." }
```

## Example

```json
{
  "type": "<LibraryName>",
  "name": "myNode",
  "setting": {
    "settingName": "value"
  }
}
```

## Development

- `npm install` — install dependencies
- `npm test` — run unit tests
- `npm run build` — produce `dist/bundle.js` and `dist/deno-bundle.js`

## Caveats

- Any limitations, rate limits, or server-only operations.

See `skill.md` for the machine-readable description used by AI agents.
```

### Where to place `README.md`

Place it at the root of the plugin repository, alongside `package.json`:

```
my-plugin/
├── src/
│   └── index.ts
├── tests/
├── README.md       ← here
├── skill.md
├── package.json
└── webpack.config.cjs
```

Commit it alongside the plugin source so it stays in sync with every published
version.
